# 품질 평가 세트 (`insia eval`)

프롬프트, 채널 가이드, 모델, 코드를 바꾸면 초안 품질이 조용히 나빠질 수 있어요. 이 폴더는 그걸 **바꾸기 전과 후에 같은 케이스로 돌려 비교**하는 평가 세트예요. 케이스마다 실제 파이프라인(`insia run`과 같은 경로)을 돌리고, 사람이 매번 확인하던 것들(블라인드, 금지 표현, 지어낸 수치, 가정 표시, 채널 형식)을 **코드로 똑같이** 채점해요.

- mock 모드: 무료·오프라인이에요. 평가 도구가 제대로 도는지와 결정적 검사를 확인해요.
- live 모드: Anthropic API로 진짜 초안을 만들어 채점해요. **돈이 들어서** `--max-cost-usd`가 꼭 필요해요.
- 평가는 임시 워크스페이스에서 돌아서 **내 워크스페이스(보관함·사용량)는 건드리지 않아요.**

## 빠른 시작

```bash
insia eval list                                   # 케이스 목록
insia eval run --mode mock                        # 무료로 전체 한 바퀴 (1초 안팎)
insia eval run --mode live --dry-run              # live로 돌리면 얼마쯤 드는지 먼저 보기
insia eval run --mode live --case very-short-brief --max-cost-usd 8     # 한두 케이스로 시험 (실측 비용 확인)
insia eval run --mode live --max-cost-usd 120 --out evals/results/baseline-2026-09   # 전체 기준 결과 만들기
insia eval compare evals/results/baseline-2026-09 evals/results/<이번 폴더>          # 바꾼 뒤 비교
```

설치 전이면 `PYTHONPATH=src python -m insia_agents eval …`로 똑같이 돼요. 결과는 기본으로 `evals/results/<시각>-<모드>/`에 쌓이고, 이 폴더는 git에 올리지 않아요(`evals/.gitignore`). 오래 둘 기준 결과는 이름을 붙여 보관하세요.

### 자주 쓰는 옵션

| 옵션 | 뜻 |
|---|---|
| `--case ID` | 이 케이스만 (여러 번 쓰거나 쉼표로 구분) |
| `--channels linkedin,instagram` | 이 채널만 |
| `--baseline 폴더` | 이번 실행을 지난 결과와 비교해 보고서 맨 위에 회귀를 보여 줘요. `--case`·`--channels`로 일부만 돌리면 **돌린 케이스·채널만** 비교해요(전체 기준과 비교하는 작은 시험도 통과할 수 있어요) |
| `--max-score-drop 5` | 평균 검수 점수가 이만큼 넘게 떨어지면 실패 (기본 5점) |
| `--reps 2` | 케이스마다 두 번씩 (live 점수 흔들림을 줄여요, 비용도 2배) |
| `--resume --out 폴더` | 중간에 멈춘 실행을 이어서 해요. 케이스 파일·채널·모드가 그대로인 끝난 실행만 다시 쓰고, 나머지는 다시 돌려요. 예산 상한에는 이 폴더에서 이미 쓴 비용(다시 쓴 실행 + 다시 돌린 이전 시도)이 먼저 들어가요 |
| `--estimate-from 폴더` | 예상 비용을 지난 live 평가의 **실측** 비용으로 계산 |
| `--timeout-s 1800` | live 실행 1번의 최대 시간 (넘으면 멈추고 '시간 초과'로 기록) |
| `--judge --judge-model claude-sonnet-5` | (돈이 들어요) LLM이 이번 최종본과 기준 최종본을 짝지어 비교 |
| `--json` | 요약을 JSON으로 (진행 줄은 stderr) |
| `--yes` | live 시작 확인을 묻지 않아요. 터미널이 아닌 곳(cron·스크립트)에서는 원래 묻지 않고 `--max-cost-usd`를 동의로 봐요 |

종료 코드: `0` 필수 조건 전부 통과·회귀 없음 · `1` 필수 조건 실패, 평가 못 한 채널, 기준 대비 회귀, 예산으로 멈춤, API 자격 증명 없음 · `2` 잘못 씀(옵션, 케이스 파일, live에 예산 상한 없음, 가격을 모르는 모델) · `130` 중단.

## 어떻게 채점하나

값싸고 설명할 수 있는 **결정적 검사**가 먼저예요. 같은 초안이면 언제나 같은 결과가 나와요.

1. **형식·브랜드 검사** — `channels.check_format`에 케이스의 브리프·프로필을 넣어 돌려요(대시보드·`insia check`와 같은 코드). 채널 형식(분량, 소제목, 이미지 자리, 해시태그 수, 첫 줄 길이, 본문 링크), 금지 표현, 필수 문구, 사업계획서 블라인드(실명, 경력 맥락의 학교·직장명). 보고서에 검사 id별 통과율이 나와요.
2. **들어가면 안 되는 말 / 꼭 들어갈 말** — 띄어쓰기·대소문자를 무시하고 제목·본문·해시태그에서 찾아요(팀원 실명, 메모의 과장 표현 등).
3. **수치 근거 확인** — 본문의 수치 주장(`%`, `%p`, `원`·`달러`(천·만·억·조 포함), `명`, `개`·`개소`·`곳`, `건`, `배`, 기간 `년`·`개월`)을 모두 찾아 하나씩 판정해요. `3천여 곳`, `5만여 명` 같은 어림수도 수치예요(3천여 = 3,000~3,999로 맞춰 봐요). 단위 뒤에는 조사·어미만 와야 해서(`30%의`, `3년간`, `1만 원대`) `3원칙`, `4년제`, `20개년` 같은 낱말은 수치로 세지 않아요.
   - **근거 있음**: 같은 값이 리서치 팩(근거 문장·출처 제목)·회사 프로필·사용자 자료에 있어요. 반올림은 적힌 자릿수까지만 봐요(`116만 개`는 `116.3만개`와 맞고, `60%`는 `59.1%`와 안 맞아요). 리서치 팩의 `gaps`(확인 못 한 것)와 **브리프는 근거로 치지 않아요** — 브리프는 요청이라서, 메모에 적힌 '들은 이야기'를 그대로 쓰면 근거 없음이에요.
   - **자료가 확정하지 않은 값**: 사용자 자료·프로필이 스스로 `검토 중`, `확정 전`, `미정`, `가정`, 목표·예정 수치라고 적은 값은, 초안도 가정·검토 중이라고 밝혀야 근거 있음이에요. 확정처럼 쓰면 **근거 없음**(보고서에 "자료에선 확정 전"이라고 나와요)이고, `assumption_marked`도 이 값을 면제하지 않아요. 리서치 팩의 값은 이렇게 보지 않아요(확인 못 한 것은 `gaps`로 가요).
   - **확인 필요 표시**: 그 문장에 `확인 필요`가 있어요.
   - **가정 표시**: 그 문장(표는 그 행, 문단·표 바로 뒤의 `※` 줄 포함)에 가정·예시·가상·시나리오가 있거나, **수치에 바로 붙은** 목표·예정·계획이 있어요. `목표`는 수치 바로 앞(`목표 매출 3억 원`, `1차년도 목표: 매출 1.2억 원`, 표의 `| 매출 목표 | 1.2억 원 |`), `목표`·`예정`·`계획`은 수치 뒤 세 낱말 안(`2,000개 확보 목표`, `월 3만 원으로 책정할 예정`)이어야 해요. `목표 시장`·`목표 고객`(시장 이름)이나 `12월 출시 예정인 신제품은 고객 5,000명이 …`처럼 수치와 떨어진 말은 가정 표시가 아니에요. 표시 말은 낱말로 찾아서 `가정용`, `가정에서`, `가정간편식`, `가상화폐`는 가정 표시가 아니에요.
   - **근거 없음**: 위 어디에도 해당하지 않아요. 지어낸 값일 가능성이 높아요. 보고서에 문장과 함께 나와요.
   - 연도(`2024년`, `'24년`), 일정 표시(`출시 2년 차`), 10 이하의 정수 개수(`브리프 1건`, `4개 채널`, `대표 포함 3명`)는 문장 표현이라 주장으로 세지 않아요. 출처 줄(`출처: …`, `- [s1] …`), 해시태그 줄, 이미지 자리, 캐러셀 비주얼 지시는 건너뛰어요.
   - **인용률**: 출처가 필요한 수치 중 같은 문단(표는 그 행)에 출처(`[s#]`, `출처`, `자사 자료`, `…에 따르면`, 「보고서 제목」, `같은 조사`, 기관·발행처 이름)가 있는 비율이에요. 네이버·인스타그램·링크드인·Meta 같은 플랫폼 이름은 SNS 글이 다루는 대상이라 그것만으로는 출처로 치지 않아요.
4. **자리표시** — `○○`와 `[대표자 성명]`, `[확인 필요: …]` 같은 대괄호 자리표시를 세요(`[s1]`, `[이미지: …]`, `[데모]`는 빼요).
5. **과정 지표** — 검수 에이전트의 최종 점수·통과 여부, 수정 횟수, 최종 검수에 남은 critical 이슈, 비용(USD), 걸린 시간, 응답한 모델(요청과 다르면 경고).
6. **LLM 비교 채점 (선택, 유료)** — `--judge`를 켜면 다른 모델(기본 `claude-sonnet-5`)이 이번 최종본과 `--baseline`의 최종본을 A/B 순서를 섞어 비교해요. 누가 기준인지 알려 주지 않고, 무승부·둘 다 부족도 허용하고, 길이를 좋게 보지 말라고 해요. 비용은 따로(`judge_cost_usd`) 기록하고 같은 예산 상한에 포함돼요. 사람이 판정한 몇 쌍과 먼저 맞춰 본 뒤 믿으세요. 테스트에서는 절대 부르지 않아요.

### 조건 종류 (`must` · `should`)

`must`는 하나라도 실패하면 실행이 실패(종료 코드 1)하는 조건, `should`는 목표치예요(보고서에 나오지만 실패로 치지 않아요). 조건마다 `channels`(비우면 케이스의 모든 채널), `modes`(`["live"]`처럼 모드 제한), `note`(왜 보는지, 보고서에 나와요)를 붙일 수 있어요.

| type | 값 | 통과 기준 |
|---|---|---|
| `checks_pass` | `checks: [id…]` | 그 검사가 실행됐고 모두 통과 (id는 `insia check`에 나오는 것: `length`, `psst_팀구성`, `title_keyword`, `no_link`, `slides`, `banned_words`, `required_phrases`, `blind_names` …) |
| `all_checks_pass` | | 모든 형식·브랜드 검사 통과 |
| `not_contains` / `contains` | `values: [말…]` | 하나도 없음 / 모두 있음 |
| `max_unsupported_numbers` | `value: N` | 근거 없는 수치 N개 이하 |
| `min_placeholders` | `value: N` | 자리표시 N개 이상 |
| `assumption_marked` | `units: ["원"]`, `markers: ["가정"]` | 리서치 팩·사용자 자료가 확정해 주지 않은 그 단위 수치는 모두 표시가 있음. 자료가 '검토 중·확정 전'이라고 한 값도 표시가 필요하고, 표시 말은 낱말로 찾아요(`가정용`은 안 돼요) |
| `min_citation_coverage` | `value: 0.6` | 인용률 60% 이상 (수치가 없으면 통과) |
| `min_score` / `reviewer_passed` | `value: 80` / | 검수 점수 / 검수 통과 |
| `max_rounds` / `max_critical_issues` | `value: N` | 수정 횟수 / 최종 critical 이슈 N 이하 |
| `max_cost_usd` / `max_duration_s` | `value: N` | 케이스 전체 비용 / 시간 (채널 없이 케이스 단위) |

케이스에 `"facts_available": false`를 적으면 공식 수치를 구할 수 없는 주제라는 뜻이에요. 그러면 채널마다 `min_placeholders: 1`(자리표시 1개 이상)과 `max_unsupported_numbers: 0`이 **필수 조건으로 자동으로 붙어요**(`must`에 같은 종류를 직접 적은 채널은 그 값을 써요). 보고서에는 "facts_available: false라서 붙은 조건"이라고 나와요.

## 실제 나쁜 출력으로 케이스 추가하기

가장 값진 케이스는 **실제로 잘못 나왔던 초안**에서 나와요.

1. 문제 초안을 찾아요: `insia items show <콘텐츠 id>`로 본문을 보고, 실행 id로 `insia runs show <실행 id>`에서 브리프를 확인해요.
2. `evals/cases/<새 id>.json`을 만들어요(아무 케이스나 복사해서 시작하면 편해요). `id`는 파일 이름과 같게, 영문 소문자·숫자·하이픈으로.
   - `brief`: 그때의 브리프. `profile`·`documents`: 문제와 관련된 부분만.
   - **개인정보는 지우세요**: 실명·연락처·고객사 이름은 가상의 값으로 바꿔요(블라인드 케이스라면 가상 실명을 쓰고 그 이름을 `not_contains`에 넣어요).
   - `source: "real-bad-output"`, `description`에 무엇이 잘못됐는지 한두 문장.
3. `must`에 **그 문제를 잡는 조건**을 넣어요. 예: 실명이 나왔다 → `not_contains` + `checks_pass: blind_names` / 없는 통계를 썼다 → `max_unsupported_numbers: 0` / 가격을 확정처럼 썼다 → `assumption_marked`.
4. 조건이 그 나쁜 초안을 정말 잡는지 확인해요: 초안 JSON을 저장해 `insia check draft.json --profile profile.json`으로 형식·브랜드를 보고, 수치 판정은 live 결과의 `cases/<id>.json`에서 봐요.
5. `insia eval list`(형식 확인) → `insia eval run --mode mock --case <id>`(도구가 도는지) → `insia eval run --mode live --case <id> --max-cost-usd 10`(지금은 통과하는지).

케이스를 고칠 때 검사 id가 틀리거나 브리프에 없는 채널을 적으면 `insia eval list`가 파일 이름과 함께 알려 줘요.

## 결과 읽는 법

결과 폴더에는 네 가지가 있어요.

- `report.md` — 먼저 이것만 보면 돼요. **먼저 볼 것**(실패한 필수 조건, 실행 문제, 기준 대비 회귀) → 케이스·채널별 표 → 권장 목표 미달 → 검사 id별 통과율 → 근거 없는 수치 목록(문장 포함) → 케이스 설명.
- `summary.json` — 비교(`insia eval compare`)가 읽는 요약. 조건마다 `key`(예: `checks_pass:blind_names`)로 이전 결과와 맞춰요.
- `cases/<id>.json` — 케이스 입력, 최종본 전문, 수치 하나하나의 판정과 근거 위치(`research:f3`, `profile`, `document:s5`), 검수 의견.
- `runs/<id>/` — 파이프라인 기록 그대로(브리프, 계획, 리서치 팩, 채널별 최종본·검수, `events.jsonl`).

실패에는 종류가 있어요. **필수 조건 실패**는 초안의 문제예요. **평가 못 함**(API 오류, 모델 거절, 시간 초과, 예산으로 멈춤, 건너뜀)은 실행의 문제라 품질 실패로 세지 않고 따로 보여 줘요.

live 점수는 같은 입력에서도 몇 점씩 흔들려요. 보고서가 알려 주는 잡음 범위(채널 수가 적을수록 커요) 안의 차이로 결론 내리지 말고, 중요한 결정 전에는 `--reps 2`로 돌리세요.

## 비용

- **mock은 무료**예요.
- **live는 실행 전에 예상 비용을 보여 주고**, `--max-cost-usd`(평가 전체 상한)가 없으면 시작하지 않아요. 케이스마다 남은 예산을 파이프라인 예산 상한으로 걸어서, 상한에 닿으면 새 호출을 멈추고 남은 케이스는 '건너뜀'으로 기록해요. 이미 진행 중이던 호출은 끝까지 가므로 실제 비용이 상한을 조금 넘을 수 있어요.
- **가격을 모르는 모델이면 live를 시작하지 않아요**(종료 코드 2). 가격을 모르면 비용이 $0으로 기록돼 상한이 작동하지 않기 때문이에요. 새 모델을 시험할 때는 워크스페이스의 `prices.json`이나 `INSIA_PRICE_<모델>_INPUT`/`_OUTPUT`(백만 토큰당 달러)으로 가격을 먼저 넣으세요. 도중에 가격을 모르는 모델이 응답하면(서버 측 대체 등) 그 케이스 뒤에서 멈추고 남은 케이스는 건너뛰어요.
- `--resume`으로 이어서 하면 상한은 **이 결과 폴더 전체**에 걸려요. 이전 시도에서 쓴 비용이 먼저 들어가서, 상한을 새로 받지 않아요. 다시 돌리느라 버린 이전 시도의 비용은 보고서 비용 줄에 따로 나와요.
- **처음 추정(토큰 모델)**: 호출마다 실제 프롬프트 파일 길이와 녹화 샘플 실행의 산출물 크기(계획 약 6천 자, 리서치 팩 약 3만 6천 자, 사업계획서 초안 약 2만 2천 자, 검수 약 1만 9천 자 …)를 글자 1.5자 = 토큰 1개로 바꾸고, 생각(thinking) 토큰을 출력만큼 더해 `costs.py` 가격(`prices.json`·`INSIA_PRICE_*` 반영)으로 계산해요. 캐시 할인은 빼서 입력 쪽은 넉넉하게 잡혀요. 웹 검색 결과 토큰(조사 1번에 12만 토큰으로 가정)이 가장 큰 불확실성이라 **±2~3배**로 보세요.
  - 기본 모델 `claude-opus-5` 기준: 계획+리서치 약 $2.8 + 채널당(수정 1회) 사업계획서 약 $3.7 · 블로그 약 $2.0 · 링크드인 약 $1.4 · 인스타그램 약 $1.8. 케이스당 약 $4~12, **전체 12개 약 $79**(수정을 2회까지 다 쓰면 약 $103). `claude-sonnet-5`면 전체 약 $33.
- **실측 기반 추정이 더 정확해요**: 한두 케이스를 live로 돌린 뒤 `--estimate-from <그 결과 폴더>`를 쓰면 케이스별 실측 비용(없는 케이스는 채널당 평균)으로 계산해요.
- `--judge`는 채널마다 비교 채점 호출이 하나씩 더 붙어요(돈이 들어요).

## mock 결과를 볼 때

- 샘플 브리프(`sample-insia-all`)는 녹화된 실제 실행이라 수치 근거·인용률이 의미 있어요.
- 나머지는 `[데모]` 템플릿이라 수치가 대부분 `○○`이고 검수 점수는 고정값이에요. 점수로 품질을 판단하지 마세요.
- 녹화된 샘플 사업계획서의 첫 사업비 표에는 `※ 가정` 줄이 없어서, 단가 4개(월 2,500,000원 등)가 근거 없음으로 나오고 권장 목표 `max_unsupported_numbers=3`에 못 미쳐요. 녹화의 실제 약점이라 목표치는 그대로 두었어요.
- mock 템플릿은 프로필 CTA를 링크드인 본문에 그대로 붙여서, 링크가 든 CTA가 있으면 `no_link` 검사가 실패해요. 그래서 `b2b-saas-english-terms`의 링크 조건은 `modes: ["live"]`로 live에서만 필수예요(권장 목표 `all_checks_pass`에는 mock에서도 실패로 보여요).

## 한계

- 10 이하의 정수 개수는 세지 않아서 '3곳 중 1곳' 같은 작은 지어낸 수치는 놓쳐요.
- 가정 표시는 낱말과 위치로만 봐요. '가정을 꾸리다'처럼 조사가 붙은 다른 뜻의 '가정'은 구분하지 못하고, 수치와 목표 사이에 다른 수치가 끼면(`목표는 3년 안에 고객 1만 명`) 가정 표시를 놓쳐 근거 없음으로 나와요(엄격한 쪽으로 틀려요). 표 머리글에만 있는 '목표'는 아래 행에 적용하지 않아요.
- '자료가 확정하지 않은 값'은 정해진 말(검토 중, 확정 전, 미정, 잠정, 가정, 수치에 붙은 목표·예정)로만 알아봐요.
- 수치 판정은 **값**만 맞춰요. 같은 값이 리서치 팩의 다른 맥락에 있으면 근거 있음으로 보고, 리서치 값으로 계산한 파생 수치(`613.4만 × 27.2%`)는 근거 없음이나 가정으로 나와요. 근거 없음 목록은 사람이 한 번 훑어보는 용도예요.
- 인용률은 같은 문단 안의 출처 표시만 봐요. 글 끝에 출처를 몰아 쓰면 낮게 나와요.
- `not_contains`는 글자 그대로 찾아서, 같은 말이 다른 뜻으로 쓰여도 잡아요. 흔한 말(플랫폼 이름 등)은 넣지 말고 실명·학교처럼 분명한 것만 넣으세요.
- 케이스 12개 × 1회는 작은 세트예요. 통과율 몇 %p 차이는 우연일 수 있어요. 새로 발견한 문제는 케이스로 계속 늘려 가세요.
